# Shadow-compare schema-derived readiness against imperative readiness (upper_limb)

## Agent Brief

**Category:** enhancement
**Summary:** Run `validateUpperLimbReadinessFromSchema` alongside the primary `validateUpperLimbReadiness` when a feature flag is on and emit a diff audit event so the two implementations can be calibrated before promotion.

**Current behavior:**
`validateUpperLimbReadinessFromSchema` exists in `slotSchemas/upperLimbExtractor.ts` and is correct by construction (derived from `upperLimbSlotSchema` via `deriveReadinessValidator`). The system registry wires `validateUpperLimbReadiness` (imperative, regex-era) as the primary `readinessValidator` for `upper_limb`. There is no mechanism to compare the two or detect disagreements. Promotion of the schema validator to primary is gated on calibration evidence (V2-904), which in turn is blocked on the calibration runner (V2-701).

**Desired behavior:**
When `GATIOD_READINESS_SHADOW=true`:

1. After the primary `validateUpperLimbReadiness` call resolves, call `validateUpperLimbReadinessFromSchema` with the same `V2SystemFacts`.
2. If the two results disagree (`ready` differs, or `missingFields` sets differ), emit a `readiness_shadow_disagreement` audit event with `{ system: "upper_limb", primaryReady, schemaReady, primaryMissing, schemaMissing }`.
3. If the results agree, emit a `readiness_shadow_agreement` event (lightweight — `system` + `ready` only).
4. The **primary result is always used** for routing decisions — shadow disagreement never changes behaviour.
5. Shadow call errors are caught and logged as `readiness_shadow_failed`; they never surface to the caller.

The hook should live in the readiness call site in `chatServiceV2` or `policyEngine`, not inside `validateUpperLimbReadiness` itself — keeping the imperative validator unmodified.

**Key interfaces:**
- `validateUpperLimbReadiness(state): ReadinessResult` — primary; unchanged
- `validateUpperLimbReadinessFromSchema(facts): ReadinessResult` — shadow; exists in `slotSchemas/upperLimbExtractor.ts`
- `ReadinessResult` — `{ ready: boolean; reason?: string; missingFields?: string[] }` in `contracts.ts`
- `logAuditEvent` — existing audit logger
- `GATIOD_READINESS_SHADOW` — new env flag, same pattern as `SEMANTIC_CONSENSUS_ENABLED`

**Acceptance criteria:**
- [ ] When `GATIOD_READINESS_SHADOW=true` and the two validators disagree, a `readiness_shadow_disagreement` audit event is emitted with full diff payload
- [ ] When they agree, a `readiness_shadow_agreement` event is emitted
- [ ] The primary validator's result is always the one used for routing — shadow result never changes a `ready: false` to `ready: true` or vice versa
- [ ] Shadow errors are caught; no throw propagates to the caller
- [ ] All existing readiness and policy-engine tests pass unchanged
- [ ] When the flag is off (default), no shadow call is made

**Out of scope:**
- Promoting `validateUpperLimbReadinessFromSchema` to primary `readinessValidator` (blocked on V2-904 calibration)
- Adding shadow readiness for systems other than `upper_limb` in this ticket
- Modifying `validateUpperLimbReadiness` or `upperLimbSlotSchema`
