# Wire semantic shadow grader into production path

## Agent Brief

**Category:** enhancement
**Summary:** Call `gradeSemanticCase` after each live `runSemanticInterpreter()` call when `GATIOD_RUN_SEMANTIC_SHADOW=true` and emit a `semantic_shadow_grade` audit event.

**Current behavior:**
`semanticShadowGrader.ts` contains a complete grading implementation (`gradeSemanticCase`, `summarizeShadowResults`, `SemanticGoldenCase`, `SemanticGradingResult`). A test-only shadow runner exists in the test tree. Neither `runSemanticInterpreter()` nor `chatServiceV2` checks `GATIOD_RUN_SEMANTIC_SHADOW` or calls the grader at runtime. The grader is unreachable from any production code path.

**Desired behavior:**
When `GATIOD_RUN_SEMANTIC_SHADOW=true`:

1. After `runSemanticInterpreter()` resolves successfully, call `gradeSemanticCase` with:
   - The returned `SemanticInterpretation`
   - A matching `SemanticGoldenCase` from a registered golden set, if one matches `interpretationId` or `sourceHash` (no-match is valid — grade as "no golden available", which is an informational outcome, not an error)
2. Emit a `semantic_shadow_grade` audit event with `{ interpretationId, outcome, score, breakdown, hadGolden: boolean }`.
3. If the grader throws (any reason), catch and log a `semantic_shadow_grade_failed` audit event — **never let shadow work affect the user-visible response or throw to the caller**.
4. No change to `V2SessionState`, no change to the response returned to the doctor.

The `GATIOD_RUN_SEMANTIC_SHADOW` flag should mirror the pattern already used for `SEMANTIC_CONSENSUS_ENABLED` — read once from `process.env`, falsy by default, tests can set it via env directly.

**Key interfaces:**
- `runSemanticInterpreter(args): Promise<SemanticInterpreterResult>` — the call site; shadow grading should happen immediately after the `SemanticInterpreterResult` is produced, before returning it to the orchestrator
- `gradeSemanticCase(golden, interpretation, raw?)` — the grader; signature is in `semanticShadowGrader.ts`
- `SemanticGoldenCase` — the golden format; a small in-memory registry (array) is fine for the first pass; the shadow runner test tree already has example cases in `tests/v2/semanticShadow/scenarios.ts` — those should be the seed set
- `logAuditEvent` — the existing audit logger used throughout `chatServiceV2`

**Acceptance criteria:**
- [ ] When `GATIOD_RUN_SEMANTIC_SHADOW=true` and the semantic interpreter produces a result, a `semantic_shadow_grade` audit event is emitted with `outcome`, `score`, `breakdown`, and `hadGolden`
- [ ] When no matching golden exists for the input, `hadGolden: false` is recorded and the event is still emitted (informational)
- [ ] When the grader throws, a `semantic_shadow_grade_failed` audit event is emitted instead — the error does not propagate to the caller
- [ ] When `GATIOD_RUN_SEMANTIC_SHADOW` is unset or false, no grader call is made and no audit event is emitted
- [ ] Existing tests in `tests/v2/semanticShadow/` continue to pass unchanged
- [ ] The `sliceF.consensusOrchestrator.test.ts` and related tests pass — no user-visible behaviour changes

**Out of scope:**
- Excel shadow reporting (V2-809 — post-rollout)
- Batch/offline shadow runner script
- Persisting shadow results to disk or a database
- Changing the grading weights or `SemanticGoldenCase` format
